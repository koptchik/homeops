# Тестирование и deployment

## Существующая реализация и ограничения

Источник фактов — [workflow](../.github/workflows/deploy-staging.yml), [Dockerfile](../Dockerfile), [Dockerfile.test](../Dockerfile.test) и тесты в `backend/tests/`. Это описание кода, а не подтверждение последнего успешного запуска.

- Workflow реагирует на push и PR в `main`. Job `tests` собирает и запускает тестовый Docker-образ на self-hosted Linux/LXC runner.
- На push в `main` после `tests` job `publish` на `ubuntu-latest` собирает и публикует в GHCR образ с тегом SHA.
- Job `deploy` зависит от `publish`: на self-hosted staging runner выполняется вход в GHCR с `packages: read`, затем `docker pull` образа с тегом SHA текущего коммита. Временный и основной staging-контейнеры используют этот образ; повторной сборки приложения на staging нет.
- Есть временный контейнер на порту 8001, `/health`, переключение на порт 8000, повторный health check, условный rollback, health check после успешного отката, вывод логов при отказе этой проверки и [очистка образов](docker-cleanup.md). Наличие rollback в YAML не доказывает корректность всех сценариев; подготовка старого контейнера предполагает существующий staging.
- Линт, security checks, отдельные smoke tests и production deployment ещё не представлены отдельными этапами. `/health` проверяет ответ приложения, а не всю инфраструктуру.

Текущий self-hosted runner для PR расходится с целевым разделением доверия ниже. Изоляция и внешние настройки доступа по одному YAML неизвестны. Это требует отдельной согласованной работы; не описывать целевую безопасность как уже обеспеченную и не менять workflow в задаче обновления правил.

## Практика проверок

Команда Python-тестов для пользователя в активной `.venv`:

```powershell
python -m pytest -v
```

Объяснять различия `PASSED`, `FAILED`, `ERROR` и `WARNING`. Не считать предупреждение падением теста и не переносить прошлые результаты на текущую версию кода.

Перед deployment проверять текущую версию, образ, состояние контейнера и health. Для rollback учитывать ошибки промежуточных шагов и наличие действительно пригодного предыдущего контейнера. Проверка существования контейнера не заменяет проверку всей логики восстановления.

Перед разрушительным действием сначала исследовать состояние, получить кандидатов или dry-run, проверить последствия, затем удалять. После действия проверять результат.

## Ближайшие учебные шаги

1. Проверить автоматический rollback и последующий health check в Actions: соответствующие шаги уже реализованы, не создавать их заново. Ручная LAB-репетиция объясняет механизм восстановления, но не проверяет условия и порядок исполнения workflow. Планируемый следующий шаг — отдельный ручной учебный режим с имитацией ошибки после переключения, выключенный по умолчанию и не меняющий обычный deployment. Его реализация и запуск — отдельные учебные действия; перед запуском согласовать влияние на staging и способ восстановления. Успешный rollback не делает неудачный deployment успешным.
2. Составить таблицу сценариев: успех; отказ временного контейнера; ошибка запуска или health основного контейнера; ошибка rollback; отсутствие предыдущего контейнера; ошибка cleanup после успешного переключения. Сначала пройти условия по коду, затем отдельно согласовать безопасную проверку восстановления. Не проверять все аварии на рабочем staging без подготовки.
3. Перевести public PR tests на GitHub-hosted runner небольшим изменением, сохранив internal deployment отдельно. Подтвердить по запуску, где выполнился job, и что PR не получил deployment-доступ.
4. По одному добавить необходимые негативные API-тесты, lint, security checks и smoke tests. Для каждой проверки объяснить, какую ошибку она обнаруживает; не включать весь набор инструментов одновременно.
5. Зафиксировать проверенный способ диагностики и восстановления перед следующей инфраструктурной миграцией. Дальнейшие этапы — в [общем учебном плане](infrastructure-security.md#поэтапный-учебный-план-homeserverhomeops).

При разборе `if` учитывать неявный `success()`: сравнение `steps.<id>.outcome` само по себе не разрешает запуск после ошибки. Для обработки отказа нужна подходящая status-check функция; её выбор объяснять через конкретный сценарий. См. [официальную семантику status checks](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions).

## Целевая цепочка и разделение runners

Постепенная целевая цепочка: branch → PR → tests → lint → security checks → Docker build → staging → smoke tests → production. Не внедрять всё сразу. Сохранять существующие работающие механизмы до появления протестированной замены по [правилам безопасных миграций](infrastructure-security.md).

Public/untrusted CI (PR tests, lint, build validation, security analysis) должен выполняться на GitHub-hosted runners. Public PR не получает прямого доступа к домашней сети. Internal deployment (Ansible, deployments, internal infrastructure, staging и production automation) — Forgejo Runner или другой изолированный internal runner с least privilege. Не считать любой self-hosted runner безопасным только из-за его названия или labels.

Окружения lab/staging/production определены в [инфраструктурных правилах](infrastructure-security.md). Сначала изучать и проверять один переход pipeline, затем добавлять следующий. Запуск тестов, сборки и deployment выполняется в пределах [поручения пользователя](collaboration.md).
