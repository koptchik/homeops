# Проверки, Git и изменения файлов

## Проверки и актуальное состояние

При возобновлении работы проверять состояние репозитория и связанные файлы в пределах [полномочий](collaboration.md). Следующий блок выполняет пользователь либо Codex по прямому поручению:

```powershell
git status
git branch --show-current
git log --oneline --decorate -n 10
git diff
```

Не считать сведения из прошлой сессии актуальными без проверки. Локальные сведения об удалённой ветке могут быть устаревшими; разрешение на чтение не разрешает `git fetch`. Учитывать staged, unstaged и untracked файлы; не стирать чужую или незавершённую работу.

Сохранять рабочий код и полезную документацию, не ломать существующие тесты намеренно и не менять API без обоснованной необходимости. Не удалять старый механизм до проверки нового. Изменения должны решать согласованную задачу, а не переписывать HomeOps с нуля.

Учитывать связи между `.github/workflows/`, Dockerfile, compose-файлами, зависимостями Python, `backend/`, тестами, `.gitignore`, `.env.example`, README и deployment scripts. Читать только относящиеся к задаче материалы, но не анализировать изменяемый файл изолированно.

Отличать проверку чтением кода от запуска тестов, успешный шаг Actions от успеха всего deployment, работающий контейнер от отвечающего приложения. Не заявлять проверку, которая не выполнялась.

## Git и изменения файлов

Работать через отдельные ветки с понятными именами: `feature/...`, `fix/...`, `chore/...`, `ci/...`, `cd/...`.

В GitHub включено автоматическое удаление веток после merge PR. Оно не удаляет локальную ветку; локальная ссылка `origin/...` может остаться устаревшей. Перед продолжением работы и push проверять статус предыдущего PR и не считать наличие локальной ссылки доказательством существования ветки на GitHub. Push старой локальной ветки может заново создать удалённую ветку, но не откроет слитый PR повторно. Для новой задачи после merge предпочитать новую ветку от обновлённого `main`; при незакоммиченных изменениях сначала продумать их сохранение. Обновление ссылок через `git fetch --prune`, переключение и создание веток выполняет пользователь, если не поручил их Codex явно.

Перед изменениями проверять ветку и рабочее дерево. Обновление `main`, создание ветки, коммит и push выполняет пользователь, если не поручил их Codex явно.

Предлагая изменение, показывать:

- файл и участок;
- небольшой diff или подсказку; готовый блок — когда это соответствует учебной цели или прямому поручению;
- причину, ожидаемое поведение и способ проверки.

После сообщения «поменял» анализировать изменения в пределах согласованного доступа и полномочий. Само сообщение не даёт нового разрешения на shell/Git-команды; при уже порученной проверке не запрашивать разрешение повторно.

Перед коммитом проверять staged diff и не смешивать несвязанные изменения. Объяснять, какой push запускает workflow, исходя из реальных триггеров файла.

Перед `reset`, `rebase`, `cherry-pick`, merge, force push, удалением веток и переписыванием истории объяснять последствия. После отмены или восстановления операции проверять состояние через `git status`.

Workflow-файлы считать кодом: анализ → предлагаемые изменения с пояснением → применение пользователем → проверка Codex → коммит/push пользователем → проверка Actions.

## Репозитории и источники истины

Целевые роли: GitHub — публичное портфолио, HomeOps, public repositories, PR, Issues, Releases и public CI; Forgejo — private repositories, внутренняя инфраструктура HomeServer, эксперименты, local Git hosting, internal CI/CD/Forgejo Actions и mirrors. Это не требование немедленно перенести репозитории.

У каждого repository один authoritative source. Допускается одностороннее зеркало: для HomeOps GitHub → Forgejo mirror; для private infrastructure Forgejo → необязательное очищенное публичное представление на GitHub. Не создавать автоматический GitHub ⇄ Forgejo с независимыми изменениями на обеих сторонах. Публичное представление приватного репозитория требует отбора данных, а не слепого mirror; см. [границы публикации](infrastructure-security.md).

Самостоятельные HomeOps, VPN/control-plane компоненты и крупные приложения могут оставаться отдельными repositories и подключаться к HomeServer через корректные Git submodules. Не создавать просто вложенные независимые `.git`. Изменение submodules — отдельная согласованная работа, а не следствие обновления архитектурных правил.
