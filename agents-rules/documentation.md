# Поддержка этих инструкций

`AGENTS.md` содержит краткую суть проекта, цели и навигацию. Файлы в `agents-rules/` хранят устойчивые правила, согласованные решения и учебный процесс, а не журнал команд.

- При новой явной договорённости Codex обновляет соответствующий тематический файл, устраняя противоречащие старые формулировки через явное описание эволюции решения. Старые решения и требования не удалять: обозначать их как legacy/current-state или прежний план, а новое направление — как target-state, сохраняя применимые ограничения и ссылки.
- Не хранить здесь «текущую ветку», SHA последних коммитов, списки изменённых файлов, прошлые результаты тестов, временные ID образов и неподтверждённые заявления о завершении задач.
- Текущее состояние определять по репозиторию, доступным логам и свежим результатам пользователя в пределах полномочий; ближайшие действия сообщать в разговоре. README хранит проверяемый обзор реализации, тематические правила — устойчивые ограничения и решения, а не результаты последнего запуска.
- В конце рабочего блока кратко обозначать достигнутый результат и следующий практический блок. Это не повод для отдельного изменения файла на каждом сообщении.
- Изменения `AGENTS.md` и `agents-rules/` проверять чтением/diff и кратко сообщать пользователю. Файлы за пределами этих инструкций без поручения не изменять.

## Публикация изменений правил

- Постоянное разрешение на публикацию инструкций отменено. Добавление в индекс, commit, push и создание PR требуют прямого отдельного поручения пользователя; поручение обновить правила само по себе их не разрешает.
- Публиковать изменения через отдельную ветку и PR; необходимую подготовку ветки выполнять по [правилам Git](workflow.md). Не пушить напрямую в `main` и не переиспользовать ветку уже слитого PR.
- Перед коммитом проверять staged diff: в документационный коммит и PR должны входить только относящиеся к задаче изменения правил. Чужие и несвязанные изменения сохранять и не включать.
- Merge PR, включая включение auto-merge, требует отдельного явного поручения пользователя. Разовое разрешение на публикацию правил не распространяется на изменения кода, инфраструктуры или CI/CD.
- После публикации кратко сообщать результат и ссылку на PR.

## Как дополнять правила

- Сначала использовать ближайший существующий тематический файл; новый файл создавать только при реальной необходимости. Сохранять разделение ответственности и область действия: общие правила → domain rules → локальные правила каталогов, если они появятся. Не превращать локальное ограничение в глобальное и не собирать всё обратно в AGENTS.md.
- При добавлении файла обновлять навигацию в `../AGENTS.md` и указывать, когда его следует читать.
- Общие правила хранить в одном месте; в тематических документах ссылаться на них относительными Markdown-ссылками.
- Использовать смысловые заголовки без сквозной нумерации, чтобы новые разделы не требовали перенумерации остальных документов.
- Ссылки между документами должны оставаться рабочими после переноса или переименования.
- Отделять действующие договорённости от долгосрочных идей. Roadmap не является поручением на реализацию и не расширяет полномочия Codex.
- Не переносить ограничения отдельного завершённого задания в постоянные правила как бессрочный запрет на последующую согласованную работу.

## Состояние, решения и эксплуатационные знания

Явно различать: реализовано по коду; частично реализовано с указанием недостающей части; согласованный план; архитектурная идея с открытыми вариантами; долгосрочный roadmap. Конфигурация workflow не доказывает успешный deployment, согласованное решение не означает выполненную миграцию. Инфраструктурные сведения пользователя обозначать как сообщённый контекст до фактической проверки.

Значимые решения сохранять в ADR: минимум `Context`, `Decision`, `Alternatives`, `Consequences`. Цель — объяснить инженерную логику. Целевое место в HomeServer — `docs/adr/`; примеры тем: NPM → Traefik, GitHub + Forgejo, Ansible, OpenTofu, SOPS + age, runner isolation, observability. До появления HomeServer решения остаются в подходящих существующих правилах; не создавать пустое дерево или фиктивные ADR ради структуры.

Общие Network-решения, их Context, Decision, Alternatives, Consequences и learning goal находятся в [Network architecture](network-architecture.md#решения-и-учебные-компромиссы). VPN-specific модель и эксплуатация остаются в существующих VPN-файлах; общий и Network roadmap связаны ссылками. При появлении ADR сначала проверить существующую запись: переносить или дополнять её с сохранением эволюции, не создавать дубликат темы. Для каждого нового компонента фиксировать проблему, причину принятия, альтернативы, компромиссы и учебную цель; отделять принятое направление от условного кандидата.

Повторяемые эксплуатационные процедуры в будущем размещать в `docs/runbooks/`: restore container, Traefik/TLS/DNS failure, Forgejo recovery, runner failure, backup restore. Runbook объясняет причины действий, предпосылки, проверки результата и восстановление, а не только команды.

Значимые учебные аварии документировать в `docs/incidents/` по формату `Incident`, `Impact`, `Timeline`, `Root Cause`, `Resolution`, `Prevention`. Это обучение поиску первопричины, а не только отчёт о возвращении сервиса в работу.

Сохранять полезный контекст и рабочие ссылки. Проблемы существующей структуры и смысловые конфликты явно отмечать в отчёте; не исправлять архитектуру системы правил молча и не создавать параллельную систему инструкций.

## Долговременная память проекта

[HomeMemory / Knowledge Platform](homememory.md) — самостоятельный проект HomeServer, который работает с существующей системой документации. Код и собственная техническая документация HomeMemory относятся к его репозиторию; общие знания HomeServer и документы HomeOps сохраняют свои canonical-источники. Наличие описания HomeMemory в правилах HomeOps фиксирует архитектурную связь, а не место его реализации. Markdown + Git — основной версионируемый источник истины; vault, поисковый индекс и ответы AI не создают независимых canonical-копий. Целевые сущности и каталоги определены в [модели знаний](homememory.md#сущности-и-размещение-знаний), их место в общем дереве — в [структуре HomeServer](infrastructure-security.md#homeserver-и-границы-проектов).

Текущее подтверждённое состояние, целевая архитектура, ADR, планы, история и итоги сессий ведутся раздельно и связываются ссылками. Исторические решения сохраняются с признаком замены и ссылкой на актуальные; выполненные этапы требуют свидетельства результата. Итог сессии содержит полезные выводы и источники, различает планы, сообщённые действия и проверки. Он не делает автоматически актуальными README, current-state или ADR и не является журналом каждой команды. Конкретные результаты проверок допустимы в датированной записи сессии или истории, но не в устойчивых правилах.

После согласованного обновления фактов поддерживать одну canonical-запись и ссылки на неё; не размножать конкурирующие описания по чатам и vault. До создания целевых каталогов сохранять действующее размещение README и тематических правил. Будущая автоматизация импорта не разрешает переписывать canonical-документы без проверки или автоматически публиковать знания; применяются [приоритеты источников](homememory.md#приоритет-источников-и-актуальность), [границы данных](homememory.md#границы-данных-и-доступа) и существующие правила публикации.
